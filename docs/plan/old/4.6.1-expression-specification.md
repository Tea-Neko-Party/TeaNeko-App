# 拟人表达与有序发送设计

日期：2026/11/03。状态：文字表达、注解扩展、有序交付、表情包及客户端表情已完成约定实现和离线验收，随计划归档。当前代码版本为 4.6.1-l，不自动改变版本号或发布状态。[实施入口](agent-expression-stickers.md)记录完成范围，[模块说明](../../../src/main/java/org/zexnocs/teanekoagent/expression/README.md)维护当前操作，[表情包设计](4.6.1-sticker-specification.md)保存素材规格。下文保留设计依据；默认值与实际边界以模块说明及模板为准，实机体验继续验收。

## 已确认需求

- 人格决定聊天语气、标点密度、颜文字和口癖；一句完整意思可以自然拆成多次发送。
- 一轮最终答案包含特殊占位符，由后端编译并按顺序发送；不为每个分段重新请求模型。
- 允许模型建议思考、打字间隔，宿主限制实际等待，保证取消、顺序和平台确认。
- 表情包独立发送，不与文字或 at 混合，允许引用当前消息；客户端自带表情使用独立指令。
- 表情包全机器人实例共享，已启用 Agent 的 scope 默认自动收集并限流；具体规格见素材设计。
- 协议及协议内指令均允许新增独立解析类，由 Spring 服务/组件上的声明注解注册；其他按类型或策略分派的职责沿用相同扩展方式。

## 职责及现有接入点

| 层次 | 职责 | 现有基础与预期调整 |
| --- | --- | --- |
| Core 执行 | 可取消的异步等待、业务执行器、顺序组合 | 复用 ExecutionControl、taskExecutor 和 CompletionStage；缺少通用延时函数时才补轻量适配 |
| App/Client | 当前客户端的原生表情目录与内容编码 | OneBot 已有 face/mface 内容模型；补通用能力端口，Agent 不构造 CQ 文本 |
| Agent 表达 | 解析正式答案、冻结发送计划、控制节奏 | 扩展 AgentReplyPlan 的领域表示，解析与平台编码分离 |
| Agent 人格 | 按当前人格、已采用表达、对象偏好和场景生成表达约束 | 复用现有 PersonalityService/StyleObservationService，不维护第二份成长人格 |
| Agent 素材 | 提供可选择的类别、ID、描述和有效性证明 | 独立表情包服务，不把本地文件或业务服务塞入 ECS 组件 |
| Agent 交付 | 顺序、等待、原授权复核、逐段持久回执 | 汇合命令与自动回复原发送循环，复用 AgentDeliveryService |

现有 AgentReplyPlan 支持普通图文及 teaneko_reply:1 的 reply/at/plain JSON，但没有等待、表情包和原生表情类型。AgentReplySender 已要求有效平台消息 ID。原自主发言仍使用 speak/text 和零工具合同，不能直接当成支持新协议。实现时保留这三条兼容路径。

## 语气如何来自人格

每轮生成一个只含值的 ExpressionContext：当前场景、表达模式、对象偏好、建议分段数、标点偏好、颜文字/表情包倾向。来源优先级为当前明确要求、当前对象偏好、人格固定约束、已采用表达习惯、默认聊天风格；实际平台与执行约束始终由宿主决定。

闲聊默认少用句末句号，允许自然停顿、少量颜文字和已有口癖；并不要求每条都发图或每句都带口癖。解释技术、代码、链接、命令、数值和正式内容保留必要标点与完整段落，模型直接生成合适文风，后端不统一删标点、加语气词或随机拆字。颜文字与 Unicode emoji 是普通文本，不经过素材库。

沿用已采用模式中的 GENERAL/TECHNICAL/CASUAL 场景和原人格字段锁定。增加新的结构化表达偏好时先给兼容默认值，不把“对我简短些”升级为全群规则；重复输入的机器人回复不能反向增加模仿支持数。第一期不新增独立情绪模型或每轮风格改写调用。

## 最终答案协议

建议采用带版本及当轮标识的完整信封，控制行单独占一行。下面的 a7c2f9104d6e 为示例，实际标识由宿主每轮生成并固定：

```text
⟦TNK:a7c2f9104d6e|BEGIN|protocol=teaneko:expression|v=1⟧
⟦TNK:a7c2f9104d6e|TEXT|mode=reply|wait=0⟧
好呀
⟦TNK:a7c2f9104d6e|TEXT|mode=plain|wait=900⟧
我再仔细看看 (・ω・)
⟦TNK:a7c2f9104d6e|STICKER|id=stk_01J_example|mode=reply|wait=650⟧
⟦TNK:a7c2f9104d6e|FACE|id=face_smile|mode=plain|wait=400⟧
⟦TNK:a7c2f9104d6e|END⟧
```

| 指令 | 含义与合法字段 |
| --- | --- |
| BEGIN / END | 完整正式输出的开始与结束；BEGIN 声明 protocol 和 v，按注册键精确选择解析器；不允许夹带信封外正文或嵌套信封 |
| TEXT | 后续字面正文直到下一控制行；mode 为 reply/at/plain，wait 可省略 |
| STICKER | 只含已向当前请求提供的素材 ID；mode 仅 reply/plain，后面不得带正文 |
| FACE | 只含当前客户端目录提供的原生表情 ID；首期独立发送，mode 仅 reply/plain |
| wait | 发送这一段前的相对毫秒等待；不是未来日期、定时任务或任意执行指令 |

规则：

1. 只有正式 assistant 最终答案、当轮标识和完整版本信封同时匹配才进入协议解析；用户原文、引用、工具结果、记忆和推理内容都不解释为发送操作。当轮标识减少碰撞，不充当授权凭证。
2. 控制行要求独占整行、字段唯一、字段名白名单、固定参数类型；TEXT 内代码围栏及反斜杠转义的控制前缀按字面保留。只有协议解析器消费转义，不对整个回答进行替换。
3. 非信封的普通答案保持现有图文语义，旧 JSON 按旧版本解析。携带新协议开头但版本、标识或正文不合法时整轮拒绝发送，不把半截控制符直接发到群里。
4. STICKER/ FACE 不能与文字、at 或其他图片组成同一平台消息；想说“哈哈”再发图，必须是两个独立步骤。reply 的目标只由宿主当前原生消息绑定，模型不能填写任意用户、scope、消息 ID、URL 或磁盘路径。
5. 文本为空、未知 ID、重复字段、未闭合信封或未支持的内容在发送前失败；删除图片不能静默改变整段意思。编译期间先解析所有资源并取得固定版本，再开始第一段。
6. 默认最多八条平台消息、两张表情包，文本每段仍受两千字符和原总预算约束；普通旧协议保留已有硬上限。过长代码优先走原完整回复形式，不进行拟人碎片化。

## 等待、顺序与取消

wait 表示前一段真实平台回执结束后，到本段发送前的等待。使用单调时钟计时；不以平台消息时间或系统时钟回拨计算间隔。首段默认立即发出，后续未声明时按字数、人格节奏和内容类型计算有界默认值，已消耗的准备时间可抵扣；不再次为全文调用拆句模型。

模型建议等待只接受非负十进制整数，先校验数值硬范围，再按本地策略归一化并冻结。建议默认首段最多 500ms、后续默认 350–1800ms、单段最多 3000ms、全轮新增等待最多 10000ms。超过剩余交付时限时先缩短等待；原结果已经失效则停止，不为模拟打字续命。超大数值等格式错误不截断成可执行值。

每段执行为：等待 → 复核当前权限/插件/目标/原引用/人格/资料/素材版本 → 原账本占用 → 再复核实际发送条件 → 传输 → 等待真实平台确认 → 更新回执。发生取消、关闭、静默、清空间或权限变化时停止未发尾部；已经发送的内容不能撤回，未知占用不补发。等待通过借用调度器返回 CompletionStage，不使用 Thread.sleep，不占住 TaskStageChain 的同步执行线，也不在数据库事务或锁里等待。

交付协调器拥有单独的短生命周期控制与总截止时间，不复用已经随模型轮次结束而关闭的 ExecutionControl，不重置原模型/工具预算。等待中的请求仍登记原真实发起者、请求 ID 和停止标记，使 /agent stop、入口关闭及应用退出可以取消它；完成后释放自己的控制、计时任务与素材租约，不关闭借用线程池。

增加按 client、scope 和机器人账号隔离的 Agent 出站顺序协调器：接收轮次时分配稳定顺序，计划就绪后按顺序交付；无输出或失败也必须释放位置。命令、自动回复和自主文本共用，其他群继续并发。它约束 Agent 自己的发送，其他独立插件的消息不自动获得同一队列保证。队列限制长度和等待时间，取消能释放未开始计划，不让一个长延时堵住全部会话。

回复等待期间继续接收入站；后续消息不能把旧计划改投新目标。普通新消息默认按轮次顺序排队，显式取消/关闭才终止尾部。需要“新话题打断尾部”时作为可替换协调策略增加，第一期不在每段间重新请求模型决定是否续发。

## 计划、重放与历史

解析、资源选择和等待归一化只做一次。生成 ApprovedReplyPlan，固定协议版本、来源请求、顺序、正文/素材 ID、素材 revision、发送模式、等待及摘要。作为轮次的可验证结果交付；重放不随机取另一个表情包、不重算分段、不产生新的等待计划，也不在不同网关重复解析成不同内容。保留旧调用构造与普通答案行为。

在原轮次完成历史记录前生成可读的语义投影：文字保留字面正文，素材记为“表情包 ID/用途描述”，客户端表情记为其名称；协议标识和控制符不进入普通聊天记忆。原模型输出若需诊断，留在既有受控执行记录，不能冒充用户原话或平台送达。

每个实际发送步骤沿用原持久占用和回执。扩展回执负载支持素材 ID、版本和可读描述，图片文件及 URL 不进入记忆。PARTIAL 只展示已确认步骤，UNKNOWN 不声称已发；素材库被后续修改不重写当时真正使用的表情描述。重启不继续发送未决尾部，也不重演等待。

## 工具往返与“一轮输出”的边界

最终话语及所有分段是一条完整 assistant 答案。按类别选图仍需先取得具体 ID：模型先读类别，调用 sticker_list，再输出上述完整信封；沿用当前 LLM 工具循环，不另起一个回复 Agent，不逐条重新生成。没有使用表情包时不用该工具，不增加额外模型请求。

若要求从输入到输出严格只有一次模型请求，就必须由宿主提前选择候选，不能同时让模型先选类别再读取目录。本设计优先遵守用户指定的两级选择。自主发言的原零工具模式首期复用文本节奏；若将来开放类别查询，必须显式修改其预算及协议，不能借拟人功能静默开放任意工具。

## 插件与客户端边界

协议采用 IReplyProtocolParser、协议内指令采用 IReplyDirectiveParser，分别通过声明注解和现有 scanner 注册为 Spring Bean；按协议/版本及指令名精确查找。内容类型及处理器也可新增类注册，避免解析完成后仍依赖封闭类型和中央 switch。注册键、拟定注解、冲突及启用规则统一维护在[注解扩展设计](4.6.1-extension-specification.md)。IExpressionPolicy、IReplyPlanCompiler、IReplyCoordinator 分别负责人格表达、计划编译和顺序交付，实际业务规则与公共守卫继续保留。

客户端原生表情通过 IClientExpressionProvider 提供带 revision 的当前 client 目录、展示名和不透明 ID，再由平台适配编码为实际内容。普通 Unicode emoji 仍是文本；OneBot face 与需额外平台能力的 mface 分别声明支持，不通过伪造 CQ 文本绕过发送器。原生表情不占表情包库数量，不触发下载、视觉分析或自动淘汰。

首期 FACE 独立发送以简化顺序与回执；未来客户端明确支持时可扩展文本与原生表情组合，但不能因此允许表情包与文本/at 混发。不支持的 client 不提供相应目录或指令，模型不能靠自报 client ID 获得能力。

ECS 组件只保存 ExpressionContext、类别快照及 ApprovedReplyPlan 等不可变值。Feature 负责按实例声明能力；使用已有事件系统开放表达候选/计划草稿的受限修改和发送结果通知，修改后重新校验。环绕沿用 OperationPipeline/现有异步端口，不改造 TaskStageChain 为异步执行器；监听器不能替换真实目标、扩大权限或跳过确认。

本地拟人配置拟放 config/agent/expression.yml，沿用 @FileConfig、Core YAML 与环境占位符。人格风格保留在既有人格配置/观察层；该文件只控制总开关、时序和消息数量。scope 的表达开关通过原 agent 配置登记，不另建一份 scope 身份或权限表。

## 必要验收

复用现有 AgentCommandIntegrationTest、逐段回执夹具和 FakeClient：验证合法信封的完整投影与字面转义，非法输入零发送；取消/关闭使等待立即结束；同 scope 顺序与跨 scope 并发；表情包严格独立且可 reply；未知/撤销素材不发送；部分发送和重启不重发。只覆盖这些真实风险，不为每个配置字段堆叠测试。实际客户端显示、动画和间隔体验仍需实机验收。
