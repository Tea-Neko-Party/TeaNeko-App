复核更新：随后 W01 回执保护、A01 静态声明缓存和 D02 页面注册均已实施，并经[独立复核](reassessment.md)通过。下文保留首次审查的架构判断和原始缺口，不能把已关闭内容重新当成当前待办；最新实现已由单一页面声明派生导航，新增页面不再修改 App／导航分支，但仍需增加对应声明。当前 4.8.5-l 新开发不在本次关闭范围。

## 一、结论

| 维度 | 首次审查时判断 | 当时的边界与注意事项 |
| --- | --- | --- |
| Agent 架构 | 分层与职责组合已经实质落地，不只是目录拆分；组件通过既有能力和四阶段执行器生效 | 会话编排、持久化和交付仍有较高状态复杂度；不应只凭类数量或类长度评价可维护性 |
| 新增类／注解扩展 | 已有合同内的工具、组件、模型、资料来源、回复扩展和管理资源，大多可不改原核心类 | 新执行阶段、替换内建语义、专用 HTTP 协议和新顶层页面不具同等低成本；未识别的新注解不会自动产生行为 |
| 模块实际作用 | 九类组件均找到实际装配／消费链；本轮没有证据支持将其中一类整体判为无用服务 | “已装配”“本轮选择”“已实际执行”“产生业务收益”是不同状态；离线功能通过不证明线上效果 |
| 冗余与兼容 | 多数看似重叠的模块分别负责不同阶段，不能按名字合并；旧摘要有明确停用条件 | 兼容入口应记录适用宿主和退出条件；端口无默认后端不能宣传为完整产品功能 |
| 异步执行 | Stage 组合、共享预算、动态撤权、实际完成后释放等机制有效，不是简单返回 Future 的外观 | 观察取消不等于外部动作停止；阻塞前段、全入口容量和真实数据库吞吐不因使用异步 API 自动解决 |
| App/Web 后端 | 类型化管理资源、宿主授权、默认拒绝和主动适配较符合本项目的高扩展性目标 | 部分静态声明仍在高频发现；专用路由授权需改中央配置 |
| Web 前端 | 元数据表单和共享请求入口已有复用基础，但仍是显式页面装配，协议边界偏弱 | 已复现无效回执清除待确认操作；顶层页面、状态和生命周期有进一步集中声明的空间 |

建议保持现有执行和插件框架，优先修补已经定位的边界；没有依据要求改为微服务、全面响应式、另一套 Agent 框架或微前端。审查时定位的 [V484-W01 回执保护与 V484-A01 静态声明缓存](completed.md#实施收尾)已在随后实施关闭；下文保留评估时的结构依据。

## 三、Agent 架构与扩展成本

### 3.1 真实组合关系

[AgentComponentFeature](../../../src/main/java/org/zexnocs/teanekoagent/component/AgentComponentFeature.java) 将 Spring 管理的组件参数、数据键、系统、工具与资料贡献桥接到既有 `AgentFeature`；不是再创建一套业务 Bean。[AgentPluginRuntime](../../../src/main/java/org/zexnocs/teanekoagent/plugin/AgentPluginRuntime.java) 校验能力标识、插件归属、依赖、写入范围并编译管线；[AgentExecutionConfig](../../../src/main/java/org/zexnocs/teanekoagent/configuration/AgentExecutionConfig.java) 将这些来源组合到实际 AgentService。

因此以下分工值得保留：

| 层面 | 应有职责 | 本轮判断 |
| --- | --- | --- |
| Core | 通用扫描、注册、插件身份、执行控制、组合与管理合同 | Agent/App 不必复制底座；项目层边界用例通过，但不代表全部运行期语义都可由文本检查证明 |
| App | 平台无关的消息、配置、会话及 Web 管理入口 | 管理路由依赖通用 DTO／资源合同，Agent 通过适配贡献业务 |
| Agent | 模型轮次、组件选择、记忆／人格等领域决策与自己的持久化合同 | 能力分别接入主链或有明确的后台生命周期，不应移到 Core 变成通用框架细节 |
| Client / Plugin | 主动适配真实平台身份、消息、内容与业务动作 | 新客户端不能只注册名字就视为完成身份、收发和管理接入 |

宿主附加 `IAgentToolSource`／`IAgentPromptSource` 限制为一个显式组合端口，见 [extraTools / extraPrompts](../../../src/main/java/org/zexnocs/teanekoagent/configuration/AgentExecutionConfig.java#L116)；多插件贡献走 Feature。这是防止未明确组合的多个来源互相覆盖，不意味着整个 Agent 只能扩展一个工具或资料源。

### 3.2 按“尽可能不修改原类”衡量

`M_core` 表示新增一种既有扩展实现需要修改的原核心／编排类数量；`M_ui` 表示新增该能力时必须修改的既有前端组件。配置启用、依赖安装、外部模块导入与测试单独计算，不藏在“0”里。

| 扩展场景 | 应新增的实现或声明 | 当前成本判断 | 必须保留的边界 |
| --- | --- | --- | --- |
| 普通工具，含共享继承方法 | 独立 Spring 工具类、现有工具注解 | `M_core = 0`；G03 已实测支持不同 JDK 接口的继承方法 | 同目录重名拒绝、真实 advice、可信上下文、client/requires、动态条件和异步终态 |
| 可序列化组件 | `IAgentComponent`、`@TeaNekoAgentComponent`、所需 System／来源 | 现有字段和四阶段内 `M_core = 0`，普通字段 `M_ui = 0` | 组件安装与插件启用分开；参数、依赖、写入键和阶段顺序受约束 |
| 多来源工具／提示资料 | `AgentFeature` 及具体来源 | 现有组合点内 `M_core = 0` | 明确名称、权限、预算、来源撤销与重放复核，不用另一个全局 singleton 聚合 |
| 模型或模型模板 | `ILLMModel`、`@LLMModel`、配置适配声明 | 现有模型／配置协议内 `M_core = 0`；普通字段无需改 UI | 真实能力声明、凭据保护、上下文容量及失败语义不能省略 |
| 新的类型化模型输出 | 类型与已支持的字段约束声明、调用原生成服务 | 不必改中央供应商分派 | Schema 只负责结构，领域证据、权限、版本和提交仍归业务服务 |
| 回复协议、指令、内容映射 | 原 Reply 扩展接口与对应注解 | 既有合同内 `M_core = 0` | 统一编译、真实交付和回执；不能让新内容自行绕过发送守卫 |
| 定时业务动作 | `AgentTaskAction` 与自身 Policy | 原动作发现与装配内 `M_core = 0` | 不另建 Timer，不伪造动作结果，不自动扩权 |
| Skill 内容 | 现有格式的技能说明／资源与显式选择 | 通常不需新增 Java 类 | Skill 不授予文件／代码权限，依赖必须存在于最终工具集合 |
| 文件、代码、知识后端 | 对应端口、策略与宿主组合配置 | 端口内实现不需改 Agent 循环，但有明确宿主接入成本 | 真实沙箱、路径／链接、来源、取消、防重等由后端履行，不能只写接口名 |
| 通用管理资源／配置区 | `ManagementResource`、配置元数据或专用 section | 常规资源 `M_core = 0`；通用表单 `M_ui = 0` | 宿主白名单、session、插件、revision 和事务提交前复核 |
| 专用 HTTP 协议 | 新 Controller／适配器 | 仍需改中央安全白名单 | 不为了零修改成本放宽默认拒绝，见 V484-D01 |
| 顶层独立页面 | Vue 页面及入口装配 | `M_ui > 0`，须改导航与 App | 不能丢失草稿、未决操作及轮询生命周期，见 V484-D02 |
| 全新执行阶段／替换内建语义 | 新合同及宿主消费点 | 需要一次性修改原宿主，不能承诺 0 | 先证明实际替换需求，不靠越来越多固定标识和条件分支扩展 |

本项目不是任意 JAR 热插拔、任意代码沙箱或远端 UI 插件系统；这些能力不能由“支持注解”推导。普通扩展应复用现有合同，新合同才需要一次性修改消费方。

## 四、模块是否真正发挥作用

“有效”指找到真实入口、消费和状态／结果影响，不等同于证明每次模型输出都有价值。未启用或没有合格输入时不执行，往往是正确的安全和成本约束。

| 模块 | 实际职责及接入 | 功能／冗余判断 | 维护建议或未覆盖边界 |
| --- | --- | --- | --- |
| [llm](../../../src/main/java/org/zexnocs/teanekoagent/llm/framework/README.md) | 路由、模型选项、消息／工具交互及预算；类型化输出复用原调用链 | 是执行基础，不是只包装请求；结构化输出与工具参数协议不同 | 保留适配器能力声明；不要将 JSON 合法等同于事实正确或可提交 |
| [memory](../../../src/main/java/org/zexnocs/teanekoplugin/agent/cognition/memory/MemoryComponent.java) | 输入／输出 System、短中长期整理、明确事实、画像、空间及管理恢复 | 有真实读取和提交；不同层次／来源不应仅因均叫“记忆”而合并 | 继续保留证据、租约、代次、持久暂停和事务复核；真实召回收益未测 |

### 4.1 容易误判为重复或无用的功能

| 看似重复的组合 | 实际区别 | 本轮建议 |
| --- | --- | --- |
| 旧会话摘要与分层记忆压缩 | [AgentSummaryConfig:69](../../../src/main/java/org/zexnocs/teanekoplugin/agent/cognition/memory/configuration/AgentSummaryConfig.java#L69) 在实际分层 Store 存在且总开关启用时关闭旧摘要；独立宿主保留旧路径 | 没有确认默认双重摘要调用；保留兼容路径，删除前确认宿主和回退需求结束 |
| 显式事实／画像与自动长期条目 | 前者保留明确事实及来源管理，后者经过历史片段和生成整理；作用域、代次和更新策略不同 | 通过来源标识和召回去重改善阅读，不合并写入状态、权限或事务 |
| 人格学习与长期记忆中的风格观察 | 一个是人格领域的持久补正，另一个是学习输入来源；无记忆时还有独立路径 | 保留人格独立性；关注输入是否实际产生有效观察，不以空批次数量判定无用 |
| expression 与 sticker | 前者决定表达协议与交付；后者维护素材和选择 | 保持解耦；原生表情无需图库，图片交付仍遵守表达合同 |
| 定时活动与主动活动 | 前者执行持久计划；后者基于当前上下文决定是否发言 | 可共享 Agent 执行底座，不能混用领取、防重和弃言规则 |
| 旧 LLM 工具目录与 Agent 注解工具 | 旧协议用于兼容／独立宿主，Agent 主入口已走新注解注册 | 文档标清入口；未确认旧消费者退出前不直接删除兼容目录 |
| 统一结构化输出与原领域校验 | 结构服务处理格式、字段与模型终态；证据归属、主体、权限和版本由领域判定 | 六类结构输出共用服务有价值，但不能删除长期记忆提交前的证据复核 |

本轮**未确认可以安全直接删除的整块模块**。这是基于已找到消费链与兼容边界的结论，不等于每个方法和配置都不存在冗余。后续清理应给出具体无调用／无消费者证据、部署与回退边界，再按块删除。

### 4.2 如何判断运行中是否真正产生价值

优先复用现有活动和诊断入口，在同一请求／批次下区分：能力未安装、插件停用、无合格输入、已选中、真实执行、业务结果、交付未确认。对记忆观察整理推进及有效召回，对 Skill 观察实际加载与使用，对主动活动观察弃言和真实送达；不以“调用次数多”证明有效。

当前计划已有可观察日志工作，可据此补齐有必要的原因和关联号。不建议再建独立日志总线、默认记录聊天原文，或为增加活跃率绕过预算／权限。质量改善、召回效果和资源收益须另以真实场景验证，本轮未测。

## 五、异步性与可维护性

| 边界 | 现有有效机制 | 不应扩大解释为 |
| --- | --- | --- |
| 工具执行 | 真实代理调用，CompletionStage 结果展开，调用前及完成后的资格复核；G03 相关回归通过 | 所有包装成 Future 的业务都自动在独立线程运行 |
| System／轮次 | 四阶段进入既有管线，阶段结果参与组合；预算和取消控制贯穿 | 每个 System 的同步前段自动切换业务执行器；旧 A4 尚非本轮关闭范围 |
| 多实例协作 | 共用父预算和真实身份，每次交接复核来源，借用实例不被服务关闭 | 自动并行分派、持久化恢复或无限子 Agent |
| Web 管理 | [WebManagementCalls:118](../../../src/main/java/org/zexnocs/teanekoapp/web/WebManagementCalls.java#L118) 有 32 槽；真实底层阶段完成才释放控制和槽位，授权绑定当前上下文身份 | App 所有入口和前置解析都有统一全局限流，或浏览器取消即数据库回滚 |
| 后台维护／定时 | 有持久状态、有限槽位、重试／暂停等各自合同 | 旧任务取消、所有入口容量、真实数据库性能均已由本轮验证解决 |

维护性上的主要风险是**同一操作状态分散在多个边界**：配置版本、插件代次、模型完成、事务提交、平台回执、前端确认。V484-W01 正是前端把“收到 HTTP 成功”误作“已确认业务回执”的例子。优先明确状态和所有者，再拆类；不要为了缩短大类引入多个各自保存状态的协调服务。

静态声明与动态状态也应分开。Agent 工具已完成该方向的修复，组件／管理目录在审查时亦有相同调用链，已随 V484-A01 修复。新增缓存时不得将授权、连接和当前配置也一并冻结。

## 六、App/Web 是否符合高扩展性设计

### 6.1 已有值得保留的设计

- [WebManagementController](../../../src/main/java/org/zexnocs/teanekoapp/web/WebManagementController.java) 复用全局／聊天资源路由；新增常规管理资源不必增加按 Agent 业务分支的 Controller。
- [WebManagementCalls](../../../src/main/java/org/zexnocs/teanekoapp/web/WebManagementCalls.java) 在注册时拒绝重复键，运行时检查本地白名单、插件代次和真实会话；授权不只信任一个主体字符串。
- [WebSessionGuard](../../../src/main/java/org/zexnocs/teanekoapp/web/WebSessionGuard.java) 复核实际 session、管理员身份和凭据代次，适用于异步提交／返回，不依赖任意回调线程上的请求上下文。
- [ChatSettingsDirectory](../../../src/main/java/org/zexnocs/teanekoapp/web/settings/ChatSettingsDirectory.java) 已通过 `IScanner` 发布完整目录，自动投影配置管理器，也支持专用适配；这是元数据驱动的实际复用。
- [IWebFailureMapper](../../../src/main/java/org/zexnocs/teanekoapp/web/error/IWebFailureMapper.java) 与声明允许上层适配业务失败，下层 App 不必认识 Agent 的每个异常类型。管理资源与异常映射各司其职，不是重复机制。
- 会话轮换、CSRF、精确路径和最终默认拒绝仍在安全配置内。扩展便利性不应以自动开放端点为代价。

### 6.2 剩余边界与建议

以下保留审查时的判断。后续 V484-W01/A01/D02 已完成，页面已统一声明与按需加载，当前验收见[实施收尾](completed.md#页面扩展收尾)；这些历史观察不再作为重复待办。

| 观察 | 判断 | 对实现器的建议 |
| --- | --- | --- |
| 通用资源接口可组合，但专用路径写在 WebSecurityConfig | 后端“常规能力扩展”较好，“任意 HTTP 协议扩展”仍有中央修改成本 | 优先原资源合同，专用端点按 V484-D01 条件实施 |
| API DTO 在 TS 中是类型声明，成功响应未运行时校验 | 明确功能缺陷，已由坏回执复现，不只是编码风格 | 先修 V484-W01，变更协议边界优先；不必为所有只读字段立即引入庞大生成平台 |
| 顶层导航、标题、页面挂载与 opened 状态分散在中央组件 | 静态装配可以满足当前规模，但新增页面不是单文件接入 | 按 V484-D02 收敛声明；与现有控制台开发协调，避免二次导航体系 |
| `v-show` 保留访问过的页面 | 用于保留草稿和工作区状态，不能单凭未卸载断言内存泄漏 | 页面去激活需停止不必要轮询，但保留 `canLeave` 和未决操作保护 |
| App 切换 Agent 目标先调用子页 `canLeave`，子页 busy 拒绝切换 | 已有目标切换防护 | 本轮未据此报告“异步响应串到其他聊天”；不能只看子页 watch 就忽略父入口 |
| 构建给出大于 500 kB 的 chunk 提示 | 包体观察，不是功能失败或已测卡顿；本轮构建仍成功 | 新独立页可按需代码分割，先测加载影响，不为消除提示盲目拆包 |
| 4.8.4-l 正在加入通用值编辑器、目录和独立管理功能 | 属于并行实施中内容 | 本轮不把未完成的新控件标为无用，也不把之前测试视作这些新功能已验收 |

总体是“后端合同式扩展较成熟，前端页面扩展和响应状态合同仍需收敛”，不是因缺少某个流行库就不现代。下一步以实际缺陷和可重复的新增能力场景为验收，而不是框架数量。
