# Agent 插件扩展性评估

评估日期：2026/11/02。本文依据当前源码，区分已有端口与建议新增的插件能力；属于架构评估，不代表下列插件 API、加载器或生命周期已实现，不修改既有业务规格与交付比例。

## 结论与范围

实施更新：v4.6.0-l 已落实插件基础及 Agent 组合，下文“当前事实”保留改造前状态。实际 API、边界与示例统一见 [插件指南](../development/plugins/README.md) 和 [实施入口](../plan/4.6.0-plugins.md)，不把建议类名当作现有 API。

现有 Agent 具备扩展基础，但尚无统一插件管理实现。优先将能力从“替换一个总入口”调整为“多个贡献者由宿主组合”，复用原工具循环、Prompt、执行控制、事件、Timer 和专用 EasyData。内置能力也采用同一注册合同，避免内置与第三方各维护一套装配逻辑。

首阶段插件指受信任、随应用启动的 Java 模块及资源包。插件可独立开发和作为依赖接入，逻辑启停不等于卸载 Spring Bean 或类。外部 JAR 热加载、上传安装和不可信代码隔离是后续独立能力，不作为普通工具插件的前提。

## 适合开放的能力

P0 表示首批面向实际插件开发，P1 表示注册基础稳定后开放，P2 表示有明确需求后再做。

| 能力 | 适合的插件 | 建议方式 | 优先级 |
| --- | --- | --- | --- |
| 业务工具 | 查询、业务操作、外部服务接入 | 工具贡献接口返回原 LLMToolBinding；宿主统一选择、冻结 schema、校验参数和执行预算，不由插件另建循环 | P0 |
| Prompt 资料 | 项目上下文、业务说明、特定领域证据 | 资料贡献接口复用 resolve、verify、verifyReplay，携带来源和版本；多个贡献者按稳定顺序组合并受总输入预算约束 | P0 |
| 知识源 | 本地文档、远端知识服务、不同检索后端 | 将已有 IKnowledgeSource 注册为具名来源，由宿主选择允许来源；保留来源、revision 和完整性 | P0 |
| Skill | 可安装流程、业务操作说明 | 插件提供资源及目录贡献，汇总为原 Skill 快照；依赖只引用已经授权的工具，Skill 不授予权限或执行代码 | P0 |
| 任务动作 | 提醒之外的固定业务动作 | 汇总已有 AgentScheduleService.Action 为受控动作注册表，保留原权限、防重和真实回执；插件不另建 Timer | P0 |
| 监控与告警订阅 | 用量统计、指标接收、明确配置的通知 | 订阅现有 AgentTurnReportEvent、AgentTokenAlertEvent；只取脱敏快照，失败或阻塞不改变业务终态 | P0 |
| 模型供应商 | 新协议、兼容模型网关 | 延续 ILLMModel、LLMModel 注解和统一 model.yml，补登记归属与生命周期；实际 IO 必须遵守 ExecutionPolicy | P0 |
| 文件与代码后端 | 受控文件空间、独立执行环境 | 直接实现已有 IAgentFileAccess、IAgentCodeExecutor，注册时显式声明能力；宿主授权、取消与回执仍在原链执行 | P1，高风险实现单独验收 |
| 记忆与人格策略 | 查询扩展、证据排序、事实/表达候选提取 | 开放策略与候选端口，最终追加或管理仍走原权限、字段、generation 和版本仲裁；外部索引不能取代权威存储复核 | P1 |
| 触发候选 | 业务事件、特定时间/场景建议发言 | 插件只提交候选，由宿主确认来源并经过原 Gate、静默、冷却与独立任务；不能直接调用平台发送 | P1 |
| 回复展示 | 内容格式化、平台展示适配 | 先允许产生现有图文计划和受控展示建议，实际目标与回执由宿主处理；新增音视频再扩展明确协议 | P1 |
| 显式工作流 | 多实例审阅、领域处理流程 | 封装已有 AgentWorkflowService，由宿主点名调用，共享父预算；不自动分派实例或恢复不明副作用 | P1 |
| ECS System | 专用数据准备、结果校验步骤 | 首批提供能力包到组件/System 的显式装配；声明输入/写入/依赖，复用 Core 编译；任意主链替换另行设计 | 最小装配 P0；任意主链替换 P2 |

已有端口不意味着已经支持多插件同时自动装配。例如目前注册 IKnowledgeSource 后，仍需要宿主把对应工具和资料适配接入原来源。

## 建议的底层结构

以下名称表示职责建议，不是现有类名。

| 层次 | 职责 | 应避免的依赖 |
| --- | --- | --- |
| Core 通用插件底座 | 插件标识、API 兼容版本、依赖检查、注册归属、不可变目录、状态及资源拥有关系 | 不认识 Agent、模型、记忆或平台权限 |
| Agent 插件 SPI | 工具/资料/知识/任务/Skill 等类型化贡献声明，受限调用上下文与宿主适配 | 不向插件暴露内部 AgentTurn、全量 Entity 写权限或 Repository |
| 宿主组合层 | 汇总内置与插件贡献，确定启用范围、预算、排序、可信身份、生命周期和业务守卫 | 不让插件自己拼装第二套 AgentService 或替换统一 Gate |
| 功能插件 | 提供明确能力、配置及资源，借用宿主端口执行 | 不关闭共享线程池、根控制、邮箱或其他插件资源 |

第一批可增加 IAgentToolContributor、IAgentPromptContributor 等小接口，保留现有 IAgentToolSource、IAgentPromptSource 作为宿主聚合后的入口。不要把现有接口直接改成多个 Bean 后就认为完成了插件化，也不要创建一个暴露所有内部服务的巨型 IAgentPlugin 接口。

## 必须具备的插件合同

1. **身份和命名。** 插件 ID 稳定，版本和宿主 API 兼容范围分开记录；每项贡献绑定所属插件、能力 ID、顺序和依赖。内部使用插件 ID 与局部 ID 定位，协议工具名由宿主生成合法别名并检查冲突，不直接把带分隔符的内部 ID 当作供应商工具名。
2. **追加和替换分开。** 业务插件通常追加能力；完整替换人格源、历史后端等属于部署级选择，由宿主显式指定唯一实现。不能靠加载顺序、Primary 或同名覆盖悄悄删除内置能力。
3. **有效范围取交集。** 安装、全局启用、实例声明、scope 启用、当前可信权限和本轮预算共同决定是否可用。模型只提供业务参数，不声明操作者、授权 scope 或 DEBUG；业务查询目标仍按各能力既有授权合同处理。
4. **受限异步上下文。** 只传不可变来源、固定引用和必要端口；使用 CompletionStage 表达真实完成。默认借用受限的子控制，共享原预算和取消链，不交出根控制及共享资源的关闭权。
5. **资料归属与重放。** 片段携带来源和插件 revision；总输入预算省略某能力时，其关联工具不能暗中加入。复核只针对实际采用的贡献；动态插件明确实现 verifyReplay，不能统一默认放行或通过重新检索刷新旧结果。
6. **错误分级。** 可选资料或观测失败可隔离，但必须保留不完整/不可用语义；授权、来源、版本或提交验证失败必须停止，不能把异常吞成“没有资料”。宿主决定失败策略，插件不能自行提升为可信核心步骤。
7. **副作用合同。** 使用宿主固定的请求/调用 ID 防重，等待真实提交或平台回执；取消不声称回滚，不明结果不自动重试。已有任务动作 ID 保持兼容，未来持久任务还需记录动作协议版本，缺失/不兼容插件时暂停或明确拒绝。
8. **数据边界。** Agent 权威数据继续经专用 EasyData 和既有业务端口；插件自有业务数据经所属专用入口。外部检索索引返回 Agent 事实时，必须复核当前 namespace、generation 和来源资格。
9. **配置和凭据。** 模型插件的模型设置仍统一到 model.yml；业务插件可有独立 FileConfig。环境变量复用 Core YAML，敏感配置按既有规范脱敏。普通插件上下文不携带密钥，仅模型请求认证边界使用必要凭据。
10. **SDK 稳定性。** 对外发布小而明确的 API 类型和依赖，避免以实现类、Bean 名称或可变组件布局作为插件合同。先冻结公共边界，再按实际依赖拆分 API/实现模块，不为目录整齐重写全部现有服务。

## 生命周期与 ECS 开放范围

启动期加载先校验完整候选目录，确认 ID、依赖、兼容版本和冲突后原子发布。后续若支持逻辑重载，每个实际采用的插件应固定自身 revision；未被本轮使用的插件变化不应无条件取消其他业务。

禁用先停止新的路由，并让旧租约在模型、工具、副作用和发送检查点失效；随后取消或等待插件调用结束，再释放自有资源。主动作已经发生后只能记实际结果，不以重载自动重做。逻辑禁用、配置/资源重载、Bean 销毁与类卸载是不同操作，首阶段不承诺任意 JAR 的热卸载。

Core 的 SystemDescriptor 已能表达 required、writes、after，但这些声明本身不能替代授权。Agent 后续可在准入之后的数据准备、交互之后的校验等阶段开放有限步骤；真实身份、预算、固定引用、工具执行、历史提交和最终复核仍由宿主控制。插件 patch 仅能写允许的自有或显式开放组件，不能覆盖 ACTOR、授权依据、控制拥有关系或已提交结果。

同 JVM 的 Java 插件应视为受信任代码。SDK 的业务守卫与资源约定不能构成恶意代码沙箱；需要执行不可信脚本或第三方代码时，利用已有执行后端端口接独立进程/隔离环境，而不是把下载 JAR 的能力等同于安全隔离。

## 2026/11/02：组件、事件与异步拦截的组合方案

根据本轮讨论，插件以三种互补机制扩展；下列合同仍是设计提案，不表示现有 API 已实现。

### 组件与 System：声明实例具备什么能力

复用 Core 的 ComponentKey、EntitySnapshot、ComponentPatch、SystemDescriptor 和 SystemPipeline。新增宿主装配层，将 Agent 声明的能力包展开为组件初始值、System、工具、资料及监听/拦截贡献，再统一检查依赖、写入冲突和阶段顺序。内置与插件使用相同路径。

建议用 Feature 表达包含组件及默认 System 的能力包，使使用方可以只声明安装哪些能力；纯 Component 仍表示数据。不能因为某 System 所需组件恰好齐全就自动启用它：输入满足只表示可以执行，不表示该 Agent 选择或获准使用。现有 AgentDefinition 尚无这种声明字段，AgentTurnPipeline 的四步装配也仍为固定列表。

明确数据寿命：实例级组件保存不可变配置和能力选择；会话级状态按 client、scope、agent 及 epoch 隔离；轮次级组件保存本轮输入、中间资料和结果。单例 System 保持无状态，不把不同群组、用户或并发轮次的数据写入成员字段。外部服务由 System/适配器借用，组件不持有 Bean、数据库或密钥。

插件 System 从只读快照计算 patch，由宿主检查允许写入范围并提交；required/writes/after 继续由 Core 编译检查。实例安装选择与 scope 当前授权共同限制监听器、工具及拦截器，注册为全局 Bean 不等于对所有 Agent 生效。

### 事件：开放有业务含义的决策点

区分决策事件与观测事件。决策事件例如“资料候选已准备”“回复计划待确认”，提供只读可信上下文和可修改 Draft，宿主等待处理、冻结副本、重新校验来源/大小/预算/当前引用后继续。观测事件例如“轮次完成”“任务状态改变”，携带不可变快照，可异步消费，不能反过来改变已经完成的业务。

不能直接开放整个请求、Entity 或授权对象的 setter。插件可改业务候选、允许的参数和展示计划；真实身份、授权、根控制及已提交回执仍由宿主掌握。多个监听器修改同一字段时规定稳定顺序或显式合并规则；终止决策应有明确原因，后续监听不能解除宿主拒绝。

当前 EventHandlerScanner 只接受 public void 监听方法；EventService 的 async=true 处理器提交为独立任务，外层 pushEventWithFuture 不等待其完成。第一阶段可修改事件只使用有序同步监听，完成通知后立即冻结；远程异步决策使用下述 Stage 端口。需要异步事件监听时再为 Core 增加明确等待 CompletionStage 的合同，不能只让现有监听方法返回 Stage。事件任务完成也不等于业务获准，宿主仍须读取取消/决策结果。

### Stage 链：开放异步操作的前后及环绕处理

提供类型化命名操作及拦截器，建议表达为 Operation<I,O> 与 StageInterceptor<I,O>，由 input、受限 context 和 next 返回 CompletionStage<O>。链在调用前根据不可变注册快照构建，允许前置转换、环绕计时、结果转换及受控故障处理。已经创建的 CompletionStage 图不能通过追加 thenApply 原地改写内部后续流程。

2026/11/02：经进一步核对，Core 现有 TaskStageChain 的约束是同一次阶段链在单线程调用栈中推进；执行期间允许提交异步任务。现有 CommandExecutor 已在链内同步调用命令方法，将其返回的 CompletionStage 放入 Invocation，再在任务结果之外通过 thenCompose 等待业务完成。因此，支持异步业务本身不要求重写 TaskStageChain，也不要求把原 process 方法统一改为返回 CompletionStage。

现有 chain.next() 返回 ITaskResult，后置代码包围的是同步调用；若它只启动异步业务便返回，后置代码不自动包围业务最终完成。TaskService 也支持 callable 返回 null、稍后显式 complete 的延迟完成方式，这可以延迟任务 Future 完成，但不会让已经退栈的后置代码重新执行。需要最终结果处理时，可以组合 TaskFuture.asStage()/fromStage 或显式业务 CompletionStage；仅观察时安装完成回调，需要转换结果时必须让宿主继续使用转换后返回的 Stage。

首阶段保留原链，复用现有 namespace、显式阶段列表与执行服务完成同步拦截。只有实际需要异步前置校验、完整业务计时、异步结果转换或受控短路时，才增加小型类型化异步操作/拦截端口，由宿主构建并等待其返回阶段；采用 CommandExecutor 已有的调用与完成分离方式接入，不让插件接触其私有 Invocation，也不再引入第二套任务调度或重试框架。异步节点使用不可变结构和独立调用上下文，不能在回调中继续使用原 TaskStageChain 的可变 index 推进链。

若某类任务明确要求整个环绕过程停留在同一线程，也可以在同步链内有界等待子任务，再执行后置代码；此时原接口足够。该选择必须明确超时、取消和等待依赖，不能持有数据库事务/锁等待远端 IO，也不能让受限执行池中的父任务等待只能由同一饱和执行池运行的子任务。首阶段不通过普遍增加 join 将现有非阻塞业务改为阻塞。

任务调用完成与异步业务完成应分别观测：现有 CommandExecutor 的底层调用任务先完成，外层命令 Stage 才代表完整业务。未来 Web 应跟踪外层业务的 runId 及返回阶段，不能仅按底层调用任务结束就显示命令已完成。若将来确需 Core Task 本身统一承载异步业务全生命周期，再单独设计类型化异步提交适配及状态仲裁，覆盖同步抛错、立即完成、迟到回调、取消、过期与重试的竞争；不在普通插件接入中顺带更改全部任务的完成语义。

统一规定：

- next 至多调用一次；缓存等允许短路的只读操作显式声明可以零次调用，写入、命令和发送不能伪造完成。重试仍由宿主根据预算、幂等和副作用状态决定。
- 返回 Stage 包含完整异步处理及清理；不能启动后台工作后提前返回成功，不能依赖线程局部变量传递身份，也不能在 Stage 完成前关闭借用资源。
- 顺序及依赖可验证，环绕顺序例如 A → B → 实际操作 → B → A；相同顺序使用稳定 ID 决定，不依赖 Bean 扫描顺序。
- 取消、授权失效、来源失效及版本冲突不被包装为成功；必要守卫在可扩展链外及实际提交点继续执行。
- 首批开放具名的知识检索、资料准备或格式化操作；模型、工具等后续按明确合同接入，不对任意私有方法开放反射改写。

三种机制共享插件身份、revision、启用范围及调用租约。System 调用具名操作，操作内部运行拦截链，决策事件是其中一个明确节点；同一逻辑操作只执行一次，不再各建一套检索、预算和执行器。

建议首个知识插件同时演示：实例配置组件、轮次证据组件、资料准备 System、候选资料决策事件、知识检索计时/缓存拦截器。缓存命中仍复核当前授权和资料版本。管理页面的查询、操作及状态订阅按 [Web 管理接口预留设计](web-management-api.md) 复用这些能力。

## 建议实施顺序

| 顺序 | 完整交付单元 | 必要验收 |
| --- | --- | --- |
| 1 | 注册底座、最小能力包/组件/System 装配、类型化工具/资料贡献和宿主聚合；内置记忆/历史/命令走同一路径 | 两个插件同时启用，内置工具仍在；重名/依赖冲突有确定结果，原权限与总预算不变 |
| 2 | 完成一个实际知识查询插件，包含资料决策事件和一条异步操作拦截链，从配置到正式回复闭环 | 能独立开发接入，省略/禁用/来源变化不会越权或回灌；next 不重入，事件修改后重新校验 |
| 3 | 扩展具名知识源、任务动作、Skill 资源贡献、模型适配与监控订阅 | 多插件共存、稳定注册及真实异步终态；任务仍使用原 Timer 和防重 |
| 4 | 增加受控的逻辑启停、目录快照、调用租约及资源回收 | 禁用后的迟到结果被拒绝，不影响无关插件；关闭不误关共享资源 |
| 5 | 根据实际业务增加策略、触发、展示、工作流及更多受控 ECS 阶段 | 有明确使用方，写入/发送仍经过宿主检查；不为通用性堆叠空接口 |
| 6 | 确有外部安装和不可信代码需求后，再做独立 JAR 加载或进程插件 | 分别验证包发现、依赖隔离、版本兼容、卸载与进程权限，不能复用逻辑禁用的结论冒充通过 |

测试重点是多插件组合、权限/代次、共享预算、异步故障和禁用资源回收；不为每种贡献 DTO 或机械分支新增重复用例。本轮仅维护设计文档及计划阅读索引，未改业务代码、未运行构建或真实模型。
